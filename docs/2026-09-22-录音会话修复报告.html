00 · 摘要与变更总览

四组修复，一条主线：让「每场录音」都独立、完整、可落盘

核心问题出自同一根线：录音会话（session）与 Vosk 识别器之间存在生命周期错配—— 识别器一生只创建一次，却在每场录音结束时就交走置空，于是从第二场起实时转写静默消失，收件箱随之恒空。 修复的同时，把「停止 → 立即再开录」这条容易互相踩踏的路径做了彻底隔离。

01 · 缺陷 / 高危

第二次录音开始，实时转写永远消失

根因：Vosk 识别器只在「模型首次加载完成」的异步回调里创建一次； 而每次「停止」的收尾都会把 _voskRecognizer 置空、_voskReady 置 false（交后台做末句收尾并释放）。 第二次开始录音时，初始化入口因 _initStarted 标记直接返回——没有任何代码再创建识别器。 结果是：第二场起音频照常落盘，但实时转写恒缺，行动收件箱恒空。 

// 旧实现（问题所在）：
// ① 识别器只在“模型首次加载完成”的回调里创建一次
_bootstrapTask.ContinueWith(t => {
    ...
    _voskRecognizer = new VoskRecognizer(_voskModel, 16000f);
    _voskReady = true;
});

// ② 每次 Stop 的收尾都会把它交走、置空
_voskRecognizer = null;
_voskReady = false;

// ③ 第二次 Start 时 InitRecognizerBackground() 因 _initStarted 为 true 直接 return
//    → 识别器永远不会再被创建 → 收件箱恒空

修复：抽出 TryCreateSessionRecognizer()——模型常驻复用、识别器每会话一个： 初始化入口每次会话都会尝试补建；模型加载完成的回调也复用它（内部保证「先识别器、后 ready」的赋值顺序）。 会话识别器在收尾完成 FinalResult() 后立即 Dispose()，原生句柄不再积压到下一场。 

private void TryCreateSessionRecognizer()
{
    lock (_lock)
    {
        if (_voskModel == null) return;       // 模型仍未就绪：等 bootstrap 完成时再建
        if (_voskRecognizer != null) return;  // 本会话已有识别器
        _voskRecognizer = new VoskRecognizer(_voskModel, 16000f);
        _voskReady = true;
    }
    RaiseStatus();
    _asrSignal.Set(); // 唤醒泵线程回灌 pending 缓冲
}
02 · 并发硬化

「停止后立即再开录」：会话之间严格隔离

旧结构里，停止的资源快照发生在后台线程，而「停止 → 再开录」只需要两次操作、间隔可以很短。 一旦新会话在后台快照之前启动，快照就可能把新会话的资源当成旧会话抓走； 共享的 ASR 泵旗标也可能让旧收尾把新泵误关。修复把三类交叠全部堵死：

  • 同步快照——Stop() 在同一把锁内完成状态翻转与资源快照（设备 / 写入器 / 识别器 / 泵 / 会议状态 / 会话代数），后台收尾只认快照里的旧资源。
  • 每会话独立 ASR 泵——AsrPump{ Stop, Thread } 随会话创建与移交；新会话永远建新泵，旧收尾只 Join 自己的泵。
  • 会话代际守卫——每次 Start 递增 _sessionGen；会议状态的异步更新与收尾写回先核对代数，过期结果一律丢弃，新旧会话的 LLM 状态绝不串台。
  • Vosk 调用串行化——AcceptWaveform / FinalResult / Dispose 统一经 _voskIoLock（纵深防御）；收尾用 Monitor.TryEnter(…, 3000) 有界等待，极端卡死也不拖死停止流程。
  • 退出收尾有界等待——Dispose() 等待收尾任务至多 5 秒：退出场景下 WAV 头（RIFF 长度）写完整、识别器不被半途释放。
private void Stop(bool raiseEvent)
{
    SessionSnapshot snap;
    lock (_lock)
    {
        if (!_recording) return;
        _recording = false;
        _watchdog.Stop();
        _refineTimer?.Stop();
        snap = TakeSessionSnapshotLocked(); // 同步冻结旧会话，新会话与后台收尾零交叠
    }
    ...
    var task = Task.Run(async () => await StopInternal(snap, raiseEvent));
    lock (_lock) { _stopTask = task; }
}
03 · 路径修正

录音目录：便携与安装两种场景都写对了

数据文件此前已统一收口到 AppPaths（便携 = exe 旁 data\，否则 %AppData%）， 但录音目录仍是两处写死的 exe 目录拼接（ConversationCaptureService 与 AudioCaptureService）。 安装到 Program Files 等只读位置时会静默写失败。现已新增并统一切换： 

// AppPaths：与数据目录同策略
// 便携模式（exe 旁有 data\）  → exe 旁 Recordings\（沿用历史布局）
// 漫游模式（安装到只读位置） → %AppData%\TimeTask\Recordings
public static string RecordingsDir => _recordingsDir.Value;

现有用户的录音文件位置不发生迁移；新写入自动落在正确一侧的目录。

04 · UI 修复

会议助手面板：三种入口行为归一

此前「会议实时要点」面板只在点主窗口按钮开录时出现——用全局热键（Ctrl+Alt+R）或托盘开录时不会显示。 现改为由录音状态统一驱动：ApplyRecordingUiState(recording) 在按钮 / 热键 / 托盘三条路径上表现一致， 且主窗口的 1 秒刷新会顺带自愈校正（窗口在录音中途被打开也能正确显示）。另修正一处文案括号残缺 （「…可忽略）」）。 

// 状态事件可能来自后台线程（如超时自动停止），统一切回 UI 线程
private void OnCaptureStatusChangedForButton()
{
    if (!Dispatcher.CheckAccess()) { Dispatcher.BeginInvoke(...); return; }
    RefreshRecordButton();
    ApplyRecordingUiState(svc != null && svc.IsRecording);
}
